# Decision paper: a signed macOS application (#121)

Status: **investigation only. No credential has been created or used, and no application signing has begun.** This paper is for the owner's decision.

## The question

Does a signed and notarized `.app` give users something the Homebrew-installed CLI (`brew install syncom-systems/flight/flight`, or the release tarball) does not, in proportion to its cost and to its effect on the release guarantees?

## What a user gets today

- `brew install syncom-systems/flight/flight`: the binary, tmux as a dependency, the guides, the service templates. Homebrew fetches with its own downloader, so the files carry no download quarantine flag and Gatekeeper does not block them.
- The release tarball downloaded in a browser carries the quarantine flag; the documentation says to clear it (`xattr -d com.apple.quarantine`). It is built by the release workflow and has a verifiable GitHub build attestation (no signing key exists).
- Flight's interface is a terminal program. Everything runs in the user's own terminal; services are launchd jobs the user loads from a template.

## What an application bundle would add

| Benefit | Needs | Notes |
|---|---|---|
| Download and drag to Applications; no Gatekeeper warning from a browser download | Developer ID signature, hardened runtime, notarization, stapling | The one thing a bundle gives that Homebrew does not for people who do not use Homebrew. |
| Dock icon, Spotlight, double-click start | A launcher | Flight is a TUI. A launcher can only open the user's Terminal (an Automation permission prompt) or embed its own terminal view: a terminal emulator is explicitly out of scope for v1 and a large new component. |
| Background node managed by macOS (login item, visible in System Settings) | `SMAppService` registration from a signed bundle | Real advantage over hand-loaded launchd plists; replaces `contrib/launchd`. |
| tmux included, nothing to install | Bundle tmux, libevent, ncurses and others, each signed with the app's identity; their licences redistributed | Possible, and a maintenance burden: every tmux or library security fix is now a Flight release. |
| Guided setup in a window | A GUI | The terminal setup of ADR-012 covers the same ground for the same audience. |

So the application matters mostly for people who do not use a terminal. Flight's interface is a terminal, so those people are not who it serves; the people it serves already have, or are offered by setup, a package manager.

## What it costs, and what it does to the release guarantees

- **Apple Developer Program membership** (paid, annual; an organisation account additionally needs organisation verification). The Developer ID Application certificate is issued under it.
- **Notarization** with `notarytool` needs either an App Store Connect API key (a `.p8` file) or an Apple ID with an app-specific password. Both are long-lived secrets. The signing certificate and its private key (a `.p12` and its password) are a third.
- **The release workflow today has no secrets** and relies on short-lived OIDC and GitHub attestations; that is a stated property of the release process and of the v1.0 contract. Signing and notarization would add production signing secrets to CI. That is exactly what the project's rules put behind an explicit owner decision. If approved, the mitigations would be: a dedicated GitHub Environment with required reviewer and branch/tag restriction, used by one job only; the certificate imported into a temporary keychain at run time; the API key scoped to notarization only; documented rotation; the attestation kept as the independent proof of provenance.
- **Apple's rules change.** Notarization and Gatekeeper requirements have changed over time and a notarization outage blocks releases; the release process would need a path that does not depend on Apple (the tarball and Homebrew would remain).
- **Maintenance**: a bundle layout, an updater story (or a statement that Homebrew is the updater), signing of every nested binary, a second macOS artifact to qualify, and the homebrew formula or a cask to keep in step. A Homebrew **cask** is the usual way to distribute an app; Homebrew's own policy toward unsigned or un-notarized casks should be checked at decision time.
- **Platform scope**: only macOS on Apple silicon is supported, so there is no Intel or universal-binary work.

## Alternatives

1. **Stay as is** (Homebrew and the tarball). No credentials, no new maintenance. Browser-download users clear the quarantine flag (documented).
2. **Signed and notarized `.pkg`** installing the CLI (and optionally the launchd job) without a GUI. Smaller than an app, but needs the same credentials and gives a smaller benefit.
3. **Signed `.app` as launcher only** (opens Terminal, registers the background node with `SMAppService`), tmux still from Homebrew. Gets the managed background node and a download-and-drag path; needs credentials; the Terminal automation prompt is a friction of its own.
4. **Signed `.app` with bundled tmux and an embedded terminal view.** The "installs like any Mac app" experience; a new terminal component and a large maintenance surface; outside the v1 principles.
5. **Install script** (`curl | sh`). No signing, but teaches users to run unreviewed scripts and cannot offer the provenance guarantees the project has; not recommended.

## Recommendation

Do not build an application now. Deliver #119 (guided setup) and #120, which remove the "type commands for dependencies" friction for the people Flight serves, and gather evidence on how people actually install. Revisit if (a) users who do not use Homebrew or a terminal appear in numbers, or (b) the project decides on a graphical or embedded-terminal front end. If the owner later wants an application, option 3 is the smallest step with a real benefit (managed background node), and it would be started by a separate decision that approves the secrets and their controls, not by this paper.

## Decision requested

Choose one, in the issue:

- **A. Not now** (recommended): close #121 as investigated, keep it as the record, revisit on the triggers above.
- **B. Option 3** (launcher app and managed background node): requires approval of an Apple Developer account, the signing and notarization secrets, and the controls above. Implementation would begin only after that approval.
- **C. Option 2** (`.pkg`): same approvals.

Nothing in v1.1.0 depends on the answer.
