# Cutting a release or candidate

Applies to `vX.Y.Z-rc.N` and `vX.Y.Z`. The workflow is `.github/workflows/release.yml`; the promises it keeps are in `v1.0-contract.md` section 9.

## Controls (verified through the API on 2026-10-11)

| Control | Setting |
|---|---|
| Branch ruleset "Protect main" | Pull request required; checks `fmt`, `clippy`, `test (ubuntu-latest)`, `test (macos-latest)` required; branch must be up to date; no force push, no deletion |
| Tag ruleset "Release tags: only admins create" | `v*` tags can be created by repository admins only |
| Tag ruleset "Release tags: immutable" | `v*` tags cannot be moved or deleted, no bypass. Mistakes are fixed by a new version; the owner can lift the ruleset in the repository settings if truly needed |
| Immutable releases | Enabled: once a release is published, its assets and tag cannot be changed |
| Workflow permissions | Default read-only; the release workflow raises `contents: write`, `id-token: write`, `attestations: write` only in the job that creates the draft |
| Secrets | None used. Attestations use the workflow's short-lived OIDC identity (Sigstore); there is no long-lived signing key. Release signing with an owner-held key is a post-v1 option (#92) and needs the owner's approval |
| Publication | The workflow only ever creates a **draft**. Publishing is the owner clicking "Publish release" (or `gh release edit --draft=false`) after the checks below |
| Code scanning | CodeQL (default setup) and secret scanning with push protection are on; the release decision requires no open alerts on the candidate commit |

## Steps

1. All intended changes are merged to `main`; milestone issues are closed or consciously deferred.
2. Release-prep PR: set the workspace `version` in `Cargo.toml` (and `Cargo.lock`) to the candidate version; update `docs/releases/v1.0-readiness.md`. Merge it after the normal gates.
3. Dry run: Actions -> Release -> Run workflow on `main` runs the gates, builds and smoke-tests the packages, attests them and creates (then deletes) a throwaway draft, so a tag push cannot be the first time the pipeline runs.
4. Tag the merged commit and push the tag (admin only):

       git tag -a vX.Y.Z-rc.N -m "Flight X.Y.Z-rc.N" <commit>
       git push origin vX.Y.Z-rc.N

5. The workflow checks the tag equals the workspace version and the commit is on `main`, runs the CI gates, builds both targets, smoke-tests `flight --version`, writes `SHA256SUMS`, attests the tarballs and creates the draft (marked prerelease for `-rc`). It refuses to run over an existing release.
6. Verify the draft: download its assets, `sha256sum -c`, `gh attestation verify ... --repo syncom-systems/flight`, `flight --version` equals the tag and commit. Run Actions -> Qualify with `release_run` set to the Release run id: it verifies the attestation and walks the packages through a clean install, the distributed journey, upgrade and rollback, and (Linux) systemd services on fresh machines. Run the same scripts in `tools/smoke/` on a Mac against the downloaded asset, plus `tools/smoke/real-claude.sh` (needs a logged-in `claude`; the only check that spends account tokens, so it is run by the owner or maintainer, not in CI). Qualify also runs `multinode.sh` (containers) and `service_macos.sh` (launchd) on the packages. Record results in the readiness matrix.
7. Homebrew: after the release is **published** (never before: the formula points at published assets), update `Formula/flight.rb` in `syncom-systems/homebrew-flight` (the four URLs/versions and the two `sha256` values from `SHA256SUMS`) in a pull request there; its workflow installs, audits and tests it on macOS arm64 and Ubuntu 24.04. No credential links the two repositories; this is a manual step.
8. A candidate that passes stays a draft or is published as a prerelease at the owner's choice. Final `vX.Y.Z` follows the same path from a new tag; its publication is the owner's GO.

The generated release notes list every merged pull request; before publishing, edit the draft's notes to start with the highlights, the supported platforms and the known limitations. The draft is editable; a published release is immutable.

The stable tag is a new version (`1.0.0`), tagged on a commit whose only differences from the last candidate are the version and documentation. Its packages are different bytes, so Qualify is run again on them before publication.

A failed candidate is never edited: fix only release-blocking defects on `main` and cut `rc.N+1`.
