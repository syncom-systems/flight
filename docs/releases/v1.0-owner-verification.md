# v1.0.0 owner verification (issue #108)

Three checks that need your machines. They use the exact `v1.0.0-rc.1` release assets, and only the commands in `docs/install.md`, `contrib/launchd/README.md` and `tools/smoke/`. Nothing here installs anything outside your home directory except the launchd job in check 2, which you load and remove yourself.

Two machines: **A** (runs the orchestrator, a node and a dashboard) and **B** (a node and a dashboard). Both Apple-silicon Macs on one LAN, tmux 3.3 or newer.

## 0. Setup on A and B

Everything uses a **private tmux socket (`flv1`) and a private config directory (`~/flv1`)**. Your default tmux server, any existing `-L flight` server and `~/.config/flight` are never read or written. Keep the paths short (a Unix socket path limit of about 90 characters applies).

    export REL=v1.0.0-rc.1
    mkdir -p ~/flv1/dl && cd ~/flv1/dl
    gh release download $REL --repo syncom-systems/flight \
      --pattern 'flight-1.0.0-rc.1-aarch64-apple-darwin.tar.gz' --pattern SHA256SUMS
    shasum -a 256 -c SHA256SUMS --ignore-missing
    gh attestation verify flight-1.0.0-rc.1-aarch64-apple-darwin.tar.gz --repo syncom-systems/flight --format json | grep -E 'release.yml@refs/tags/v1.0.0-rc.1|97b7002988a6d2c0c50cc16e6875cd8d5e735671'
    tar -xzf flight-1.0.0-rc.1-aarch64-apple-darwin.tar.gz
    cp flight-1.0.0-rc.1-aarch64-apple-darwin/flight ~/flv1/flight
    ~/flv1/flight --version

(The draft is visible to you as an owner; `gh release download` works on a draft with your token.)

Precautions, both machines:

    tmux ls 2>&1 | head -3          # your own sessions; note them, nothing below touches them
    tmux -L flight ls 2>&1 | head   # an existing Flight server, if any; also left alone
    tmux -L flv1 ls 2>&1            # expected: "no server running"

Evidence for setup: the output of the `shasum`, the `gh attestation` grep, and `flight --version`. Expected: `OK` for both files, two matching lines, `flight 1.0.0-rc.1 (97b7002...)`.

Optional preflight on each machine (about a minute, self-contained, private sockets): `tools/smoke/journey.sh ~/flv1/flight` from a checkout of the tag, or skip it; it was already run on A's hardware class.

## 1. Two physical machines (readiness row 2/3)

Find A's LAN address: `ipconfig getifaddr en0` (call it `A_IP`). All commands use `--config-dir`.

**On A**

    cd ~/flv1
    ./flight orchestrator run --listen 0.0.0.0:7676 --advertise A_IP:7676 --config-dir ~/flv1/orch     # leave running in a terminal
    # second terminal on A
    ./flight orchestrator enrollment create --config-dir ~/flv1/orch                                     # bundle 1, for A's node
    ./flight node join '<bundle 1>' --name node-a --config-dir ~/flv1/node
    ./flight node run --socket flv1 --config-dir ~/flv1/node                                             # leave running
    # third terminal on A
    ./flight orchestrator enrollment create --config-dir ~/flv1/orch                                     # bundle 2, for B's node
    ./flight orchestrator enrollment create --config-dir ~/flv1/orch                                     # bundle 3, for the dashboard on B

macOS may ask to allow incoming connections for `flight`: allow.

**On B**

    cd ~/flv1
    ./flight node join '<bundle 2>' --name node-b --config-dir ~/flv1/node

    # second terminal
    ./flight ui join '<bundle 3>' --name ui-b --config-dir ~/flv1/ui
    ./flight ui run --config-dir ~/flv1/ui

## 2. launchd (readiness row 14b)

On one Mac (A is fine). Uses socket `flv1` and the config from check 1 (`~/flv1/node`, already joined); stop A's hand-run node first (Ctrl-C). If you skipped check 1, join first as above.

Precaution: this job is named `name.flight.node`. If you already installed one earlier, check first and stop here if it exists: `launchctl print gui/$(id -u)/name.flight.node 2>&1 | head -3`. The commands below use the template from the checkout, so run them in the tag's checkout (`git checkout v1.0.0-rc.1`) or copy `contrib/launchd/name.flight.node.plist` from it.

    FLIGHT_BIN=$HOME/flv1/flight
    NODE_CONFIG_DIR=$HOME/flv1/node
    LOG_DIR=$HOME/flv1/logs
    mkdir -p "$LOG_DIR" ~/Library/LaunchAgents
    sed -e "s|@FLIGHT_BIN@|$FLIGHT_BIN|" -e "s|@NODE_CONFIG_DIR@|$NODE_CONFIG_DIR|" \
        -e "s|@LOG_DIR@|$LOG_DIR|" -e 's|<string>flight</string>|<string>flv1</string>|' \
        contrib/launchd/name.flight.node.plist > ~/Library/LaunchAgents/name.flight.node.plist
    plutil -lint ~/Library/LaunchAgents/name.flight.node.plist
    grep -A1 -- '--socket' ~/Library/LaunchAgents/name.flight.node.plist      # must show flv1, not flight
    launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/name.flight.node.plist

| # | Do | Expect |
|---|----|--------|
| 2.1 | `launchctl print gui/$(id -u)/name.flight.node \| grep -E 'state\|pid'`; `tail ~/flv1/logs/node.out.log`; orchestrator `node list` | `state = running`, a pid, log says connected, `node-a` `Online` |
| 2.2 | From a dashboard create a workspace on `node-a` (`~/flv1/wa`), open it, `echo before > marker`, return to the dashboard. Note `tmux -L flv1 list-sessions` | One workspace, running |
| 2.3 | `P0=$(launchctl print gui/$(id -u)/name.flight.node \| awk '/pid =/{print $3}'); kill -9 $P0` | |
| 2.4 | Within about 15 s: `launchctl print ... \| grep -E 'pid\|runs\|last exit'`; `node list` | A new pid different from `P0`, `runs` increased, `node-a` `Online` again |
| 2.5 | `tmux -L flv1 list-sessions`; the dashboard | The same session names as in 2.2, the workspace listed, reopening shows `before` in the scrollback (the node dying does not end sessions) |
| 2.6 | Optional, the documented recovery: Wi-Fi off 40 s then on | `node-a` returns to `Online`; any pid change is recorded as it is |

Evidence: the `launchctl print` output (pid, runs, last exit) before and after 2.3; `node list` at 2.1 and 2.4; the session list at 2.2 and 2.5; the last 10 lines of `~/flv1/logs/node.out.log`.

Clean up: `launchctl bootout gui/$(id -u)/name.flight.node && rm ~/Library/LaunchAgents/name.flight.node.plist`.

## 3. Real Claude CLI: return, reconnection, restoration (readiness row 1)

Single machine (A or B), after cleaning up the previous checks (no node or orchestrator of `flv1` running; `tmux -L flv1 ls` says no server). Needs the real `claude`, logged in: `claude --version`. This uses `solo` with the private socket and config directory; it starts and stops its own processes when you quit.

    mkdir -p ~/flv1/proj && cd ~/flv1
    export FLIGHT_CONFIG_DIR=$HOME/flv1/solo
    ./flight solo --socket flv1

Three different things are checked, in this order. Do not treat one as evidence of another.

**3A. Persistence: the session survives while tmux lives.**

| # | Do | Expect |
|---|----|--------|
| 3A.1 | `n`, this machine, `~/flv1/proj`, Create; Enter opens Claude. Ask: `Remember the word PINEAPPLE; reply OK.` Wait for the reply | Claude answers |
| 3A.2 | `Ctrl-Space s` (offers a shell: accept), `echo shell-1 > marker`; `Ctrl-Space q` | Back on the dashboard |
| 3A.3 | Quit the dashboard (`q`); `tmux -L flv1 ls`; run `./flight solo --socket flv1` again | The session is still listed after quitting; on return the workspace shows running, and Enter shows the same Claude conversation on screen (the pane was never stopped), shell shows `marker` |

**3B. Reconnection: the node comes back.** While the dashboard is closed, `pkill -f 'flight node run'` (only this Flight's), then start `./flight solo --socket flv1` again: expect the workspace running, same pane content. (This is a node restart, not a restoration.)

**3C. Restoration and conversation resumption after losing the private server.**

| # | Do | Expect |
|---|----|--------|
| 3C.1 | With the dashboard open, `tmux -L flv1 kill-server` | The workspace appears as SAVED (not running); its directory and name are kept |
| 3C.2 | Select it and press Enter (restore) | A message `Continuing proj…` if Claude kept the conversation, else a prompt offering `Start a new conversation`. Either is a correct, documented outcome; record which |
| 3C.3 | Open the agent and ask: `What word did I ask you to remember?` | If it said "Continuing": Claude answers PINEAPPLE (the conversation was resumed; this is **resumption**, separate from tmux survival). If it offered a new conversation and you accepted: Claude does not know; this is the documented fallback, still PASS for restoration, but note that resumption did not occur and why it said so |
| 3C.4 | The shell surface | Restored too, in `~/flv1/proj` (fresh shell: `marker` file exists, prior scrollback does not; restoration starts new processes in the saved directory, it does not recover what was running) |
| 3C.5 | Quit the dashboard; `unset FLIGHT_CONFIG_DIR` | |

Evidence: `claude --version`; a screenshot or pasted screen text at 3A.3, 3C.1, 3C.2 and the answer in 3C.3; `tmux -L flv1 ls` before and after the kill and after the restore; the contents of `~/flv1/solo/node/workspaces.toml` (no secrets in it) and `resume.toml` after 3C.2.

Clean up: `tmux -L flv1 kill-server; rm -rf ~/flv1`.

## What counts as PASS

- **Check 1**: every row 1.1-1.8 as expected, evidence attached.
- **Check 2**: rows 2.1-2.5 as expected (2.6 is informative); new pid, sessions intact.
- **Check 3**: 3A and 3B as expected, and 3C.1, 3C.2 and 3C.4 as expected. 3C.3 resumed is the best outcome; "new conversation offered" is a PASS for restoration but is recorded as a limitation (the conversation is resumed only when the node kept its reference and Claude still has the session, `flight node run --help`) and I will not claim resumption from it.

Any deviation: do not retry silently; paste what you saw. A defect is an issue; a deliberate waiver is your explicit statement in #108.
