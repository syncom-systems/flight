# Flight v1.0 release contract

This is the promise v1.0.0 makes, and the line it does not cross. Evidence for each promise is tracked in `v1.0-readiness.md`; the work still owed is the GitHub milestone `v1.0.0`. A statement here is only kept if it has been verified; anything else is listed as unsupported.

## 1. Purpose and supported workflows

Flight is a reliable, installable, persistent terminal workspace manager for developers who use AI coding agents and shells on their own machine and on other machines they can reach and authenticate to.

Supported workflows:

1. **Start**: run `flight`; the first run sets itself up and shows the dashboard.
2. **Create and discover workspaces**: `n` creates a workspace (host, directory, Claude or shell); the dashboard lists workspaces with live state and preview, search, and the mouse.
3. **Work in surfaces**: open the agent or a shell, switch with `Ctrl-Space a` / `s`, add further shells (`S`), choose one (Tab / Shift-Tab, Enter), label it (`R`), remove one (`Ctrl-Space X`), return to the dashboard (`Ctrl-Space q`).
4. **Presentations**: tabs, splits and mouse interaction over a workspace's surfaces (`Ctrl-Space v`), with the layout remembered.
5. **Persistence**: sessions survive closing the UI and reconnecting; saved workspaces survive a lost tmux server and can be restored (`--restore`, dashboard actions); agent conversations are resumed when they still exist.
6. **Distributed**: an orchestrator, nodes on several machines, dashboards anywhere, all mutually authenticated.
7. **Saved-workspace tools**: `flight workspaces` (list, undo, snapshots, profiles, export/import).

## 2. Inclusions and exclusions

Included: agent and shell surfaces, multiple independently identified shells with optional labels, everything in section 1.

Excluded from v1.0: any other surface kind; plugin or resource frameworks; a different terminal engine; unifying the two session state machines; warm dialing and other speculative performance work; distributed workspace sync or migration; UX features beyond those above. Known limitations that do not block v1.0 are in issue #91; future ideas are in issue #92.

## 3. Supported platforms

| Platform | Architecture | Notes |
|---|---|---|
| macOS | Apple silicon (arm64) | Verified on the CI `macos-latest` runner and the maintainer's machines. Release target `aarch64-apple-darwin`. |
| Linux | x86_64, glibc 2.36 or newer | Built on Debian 12 (glibc 2.36); full test suite verified on Debian 12 and Ubuntu 24.04. Release target `x86_64-unknown-linux-gnu`. |

Requires `tmux` at or above the minimum in section 4.

Topologies: (a) one machine running everything (`flight`); (b) one orchestrator, any number of nodes and dashboards, on a trusted network (LAN or VPN) where every node and dashboard can open a TCP connection to the orchestrator. Mixed macOS and Linux nodes are supported.

**Unsupported in v1.0** (not verified, not promised): Windows; Linux arm64, musl/Alpine and glibc older than 2.36; macOS on Intel; any tmux older than 3.3 (which excludes the distribution tmux of Ubuntu 22.04 and Debian 11); exposing the orchestrator directly to the public internet; an orchestrator behind a TLS-terminating proxy; running a node from a shell or tmux instead of a service manager (works, but recovery after network changes is not promised, see `contrib/launchd/README.md`); several nodes sharing one identity; several Flight processes writing the same saved-workspaces file (the second node runs without persistence and says so).

## 4. Installation and configuration

- Install from the release tarball per `docs/install.md`, after verifying checksum and attestation. No install script, no package manager, no root.
- Dependencies: `tmux` **3.3 or newer** (the full test suite passes on 3.3a, 3.4 and macOS Homebrew 3.7b; it fails on 3.2a, one fidelity test, and on 3.1c, the end-to-end shell tests; `flight` refuses an older tmux with a message), and an OS as in section 3.
- Configuration lives in `~/.config/flight` (overridable). Roles keep separate identities.
- `flight --version` reports `flight <version> (<commit>)`.
- Services: launchd (macOS) and systemd user units (Linux) are provided in `contrib/`.

## 5. Persistence, upgrade and compatibility

- Saved workspaces (`workspaces.toml`), agent resume references, and layouts are versioned files written atomically and fsynced.
- **A Flight never destroys data it cannot understand.** A file of a newer version, a file with keys it does not know, and a file it cannot parse are reported and left untouched; saving over them is refused. Any change to a persisted file's shape moves its version (ADR-008).
- Upgrading within 1.x: older files are upgraded in place and the original kept (`workspaces.v<N>.bak`). Nothing is migrated destructively.
- Downgrading: an older Flight refuses a newer file (see above); the documented rollback restores the backup.
- Wire compatibility: peers negotiate named capabilities; a peer never sends what the other did not advertise; unknown fields are ignored. Within 1.x, messages are only added to, never changed in meaning. Version 1.0.0 is the first release, so no compatibility with earlier builds is promised; pre-release builds are not supported upgrade sources.

## 6. Security expectations

- Every connection between orchestrator, nodes and dashboards is mutual TLS 1.3 with identities pinned by key fingerprint; there is no plaintext mode and no trust-on-first-use of a connection.
- Enrollment uses a one-time bundle: a single-use token held hashed in memory, short-lived, carrying the orchestrator's fingerprint. A failed join leaves nothing behind.
- Revoking an identity (`trust revoke`) takes effect on the orchestrator immediately.
- Private keys and resume references are mode 0600; secrets are not logged or exported; imported workspace files are untrusted and start nothing until the user trusts them.
- Nodes dial the orchestrator; a node accepts no inbound connections.
- Not promised: protection against a malicious user of the same account, or confidentiality on a compromised machine; the machine's tmux server and the programs inside it run with the user's privileges.
- Vulnerabilities: report privately via the repository's security advisory feature.

## 7. Reliability and session survival

- Closing or crashing the dashboard never ends a session. Reconnecting shows the same surfaces.
- Restarting or killing the node or orchestrator does not end sessions (they live in the private tmux server); the node re-reports on return.
- A link loss is detected and shown (Stale, then Disconnected) and recovers by itself.
- Loss of the tmux server (or a reboot) ends the sessions in it; saved workspaces remain and are restored on request, in a verified directory, never in a different one.
- Resource use is bounded: terminals per interface, per node and in total; bounded queues and lossy-but-bounded terminal output under backpressure; validated message and label sizes.
- Failures are reported with the reason, not hidden: a missing directory, an unreachable host and a refused action each say what happened.

## 8. Diagnostics and troubleshooting

`flight --version`; `flight orchestrator node list`, `trust list|status`; `flight workspaces list`; `solo.log` for the single-machine mode; service logs (journal, launchd logs); the troubleshooting section of `docs/install.md`.

## 9. Release artifacts and provenance

- One tarball per supported target, `flight-<version>-<target>.tar.gz`, containing the binary, licenses, README, `docs/install.md` and `contrib/`.
- `SHA256SUMS`, and a build-provenance attestation (GitHub Artifact Attestations, Sigstore) for every tarball, tying it to the repository, workflow and commit.
- Built only by the `release` workflow from a `vX.Y.Z[-rc.N]` tag whose commit is on `main`, whose version equals the workspace version, and which passed the development gates; produced as a **draft** release; published only by the owner.
- Tags `v*` cannot be moved or deleted; a release is never re-uploaded or replaced (a defect gets a new version).
- Signing keys: none; provenance uses the workflow's short-lived identity.

## 10. Acceptance and release-blocking defects

v1.0.0 is released when: every row of `v1.0-readiness.md` marked release-blocking is PASS; the milestone `v1.0.0` has no open issue; a release candidate built by the workflow has passed clean-install and core-workflow qualification on both supported platforms; and the owner has said GO.

A defect blocks the release if it: loses or corrupts user data or saved workspaces; ends a session without the user's action under a supported condition; breaks a section 1 workflow on a supported platform; weakens authentication, trust or confinement; makes the artifact fail verification or misreport its version; or contradicts this contract. Everything else is a known limitation (issue #91) or post-v1 (issue #92). After a candidate, only release-blocking fixes are merged to the release line.
